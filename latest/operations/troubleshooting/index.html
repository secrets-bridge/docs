    Troubleshooting¶

    Common failure modes¶

    "Failed to load …" on every page¶

    Likely the api isn't reachable. Check:

    curl -fsS http://localhost:18080/readyz

    If 503, the api can see Postgres or Redis but one of them isn't ready, the response body lists which:

    {"status":"unready","checks":{"postgres":"ping failed: dial tcp ..."}}

    Login returns 401 with a valid password¶

    Check the audit log:

    JAR=...  # a cookie jar from an admin sign-in (see Bootstrap: curl -c "$JAR" on /auth/login)
curl -fsS "http://localhost:18080/api/v1/audit-events?action=auth.login" \
  -b "$JAR" \
  | jq '.[] | select(.status=="denied")'

    The metadata.error_kind tells you what's wrong:

    error_kind Meaning
    user_not_found Email doesn't exist (case-insensitive). Check SB_BOOTSTRAP_ADMIN_EMAIL
    wrong_password Password mismatch
    user_disabled local_users.disabled = TRUE
    missing_fields Body shape wrong

    Google sign-in refused¶

    A refused Google sign-in always lands on /login?error=sso with "You couldn't be signed in with that account.", whatever the reason, so the page can't reveal which emails have accounts. An admin with audit.read finds the reason in the audit log:

    curl -fsS "http://localhost:18080/api/v1/audit-events?action=auth.sso.callback" \
  -b "$JAR" \
  | jq '.[] | select(.status=="denied") | {time:.occurred_at, kind:.metadata.error_kind, purpose:.metadata.purpose}'

    The browser isn't signed in yet, so these events have the actor anonymous and no email. Match them to a person by time.

    error_kind Meaning Fix
    hd_not_allowed The ID token has no hd claim (a personal Google account) or a Workspace domain that isn't allowed Use a Workspace account, or add its domain under Admin → Sign-in
    email_domain_not_allowed hd is allowed but the email's domain isn't Add the email's domain too
    email_unverified Google didn't mark the email as verified Verify it at Google
    email_has_account The email already belongs to an account here, which hasn't connected Google The person signs in with their password and uses Connect Google on their profile
    account_disabled The account was declined or disabled A declined account can't be re-enabled from the console
    provider_disabled Google is turned off, or SB_OIDC_ISSUER is Google Turn it on, or use the env-var provider
    no_public_url No public address is set Set SB_PUBLIC_URL or save one under Admin → Sign-in
    exchange_failed Google refused the code exchange, usually a wrong client ID or secret Check the client in Google Cloud Console, replace the secret, run Test
    id_token_invalid, claims_invalid, nonce_mismatch, missing_sub Google's answer couldn't be verified Check the client ID, then Test
    iat_invalid The ID token was too old or dated in the future Check the api server's clock
    no_code The person cancelled at Google, or Google returned an error Try again
    state_cookie, state_unknown, state_mismatch The round trip took longer than 5 minutes, or finished in another browser Try again in one browser

    Two other events explain refusals that aren't in auth.sso.callback:

    • user.pending_refused: the waiting limit was reached. Approve or decline waiting accounts, or raise the limit. The events are aggregated per 10-minute window, with count, first and last.
    • sso_provider.default_role_refused: approval is off, but the default role now holds a privileged permission, so the account was created waiting for approval instead. Fix the role or pick another default.

    Test runs the same checks and shows the reason to the admin who ran it, which is the quickest way to check a setup.

    Google shows "redirect_uri_mismatch"¶

    Google stops on its own error page and never comes back, so nothing is audited. The redirect URI registered on the OAuth client must match the one Secrets Bridge sends exactly:

    https://secrets.example.com/api/v1/auth/sso/google/callback

    Copy it from Admin → Sign-in → Google → Redirect URL, and add it under Authorized redirect URIs in Google Cloud Console. The scheme, host, port and path must all match. If you change the public address, update the redirect URI at Google too.

    No "Sign in with Google" button, or Turn on fails¶

    • No public address. The login page doesn't offer Google while neither SB_PUBLIC_URL nor a saved address is set, and Turn on answers 409 provider_not_ready with missing: ["public_url"]. Set one of them.
    • Missing secret or domains. missing also lists client_secret or allowed_domains.
    • The env-var provider is Google. With SB_OIDC_ISSUER set to https://accounts.google.com, the console provider is never offered (409 env_provider_is_google). Use one or the other.
    • The api won't start after setting SB_PUBLIC_URL: the value is invalid. It must be https, with no user info, query or fragment, and plain http only for localhost with SB_ENV=dev.

    Agent job fails immediately ("agent reported failure")¶

    Read the agent's log:

    docker logs secrets-bridge-agent-1 | grep -iE "job|error|fail" | tail

    The most common cause is agent provider settings. For Vault: the agent's SB_VAULT_KV_MOUNT (default kv) has to match the provider connection's mount, otherwise the job fails with a kvMount error. For AWS Secrets Manager: the agent needs SB_AWS_REGION.

    For a deeper trace, set the agent's log level to debug:

    SB_LOG_LEVEL=debug docker compose up -d agent

    "Wraps card shows 'No wraps issued yet'" after the agent ran¶

    Two possibilities:

    1. You're signed in as the wrong user. The Wraps card only fetches when the viewer is the requester. Sign in as the user who submitted the request.
    2. The agent failed before posting the wrap. Check GET /audit-events?correlation_id=<request-uuid> for the full chain, you should see wrap.create events on success.

    "Failed to load audit events"¶

    Likely audit.read permission missing. The seed admin role has it; if you're a different user, an admin needs to grant you the audit.read permission via a role.

    # As admin:
curl -fsS http://localhost:18080/api/v1/audit-events \
  -b "$JAR"

    Expected: 200 with an array. If 403, your role doesn't carry audit.read.

    Agent stays "stale" forever¶

    Two things to check:

    1. The agent's heartbeat is reaching the CP. From the agent's network, run: 
      docker exec secrets-bridge-agent-1 wget -qO- http://api:8080/healthz
    2. The agent secret is correct. A wrong secret returns 401 on heartbeat (generic message; the audit log records error_kind=unauthorized).

    Vault read returns "permission denied"¶

    The agent uses the credentials in SB_VAULT_TOKEN or via the configured Kubernetes auth role. Check that they have read access to the secret path:

    docker exec secrets-bridge-vault-1 sh -c \
  'VAULT_ADDR=http://127.0.0.1:8200 VAULT_TOKEN=devroot \
   vault kv get secret/<path>'

    If that works but the agent gets denied, the agent token has less scope than the dev token. Adjust the policy in Vault.

    Gateway¶

    Install steps are in Gateway. Start with the pod log (kubectl -n tenant-a-uat logs deploy/secrets-bridge-gateway) and the detail view (GET /api/v1/admin/gateways/<id>), which shows each replica's last heartbeat and each connector's health.

    Gateway pod is not ready, or exits at boot¶

    Check the log for the first error:

    • identity: ... has mode ...: the identity file can be read by other users or written by its group. The Gateway accepts 0400, 0600 or 0440. The chart mounts the Secret with mode 0440 and fsGroup; a hand-written manifest with defaultMode: 0444 is refused. Fix the mode, and rotate the Gateway secret (revoke, create, enroll) if other users could read it.
    • identity: ... does not exist: the Secret uses a key other than identity.key (default identity.json). A pod whose Secret does not exist at all stays in ContainerCreating.
    • identity: ... is not a valid identity JSON object or ... is missing gateway_id or gateway_secret: the file must hold exactly {"gateway_id": "...", "gateway_secret": "..."}. Unknown fields are refused, so storing the whole enrollment response does not work. The jq -ce '{gateway_id, gateway_secret}' step in the install pipeline keeps only those two fields.
    • connector self-check did not pass; not ready until it does with status unauthorized or unreachable: the Argo CD token check (GET /api/v1/session/userinfo) failed. Check that the token Secret holds a valid token for the sb-gateway account, that base_url is right, and that the connector's egress peer lets the pod reach Argo CD. The Gateway retries before each heartbeat and turns ready once the check passes.
    • connector kind is not enabled in Release 1: the connectors file names eso or rollout. Release 1 binds argocd only.
    • No heartbeat accepted within SB_GATEWAY_CP_UNREACHABLE_AFTER (default 2m): the control plane is unreachable. Check cp.endpoint, the cp.egress.cidrs NetworkPolicy peer and, for a private CA, cp.caExistingSecret.

    Gateway refuses to start: over-privileged¶

    A log line refusing to start: connectors: credential is over-privileged (or self-check could not prove the credential cannot read secrets) comes from the Kubernetes self-check. It runs only for the Release 2 eso and rollout connectors, which need SB_GATEWAY_ENABLE_R2_CONNECTORS=true; a Release 1 Gateway built from the chart has no Kubernetes access and never runs it.

    The Gateway refuses to start when its service account can use any verb on secrets, or any write verb on a resource a connector reads, or when a review call fails. There is no override. Remove the grant from the RBAC bound to the Gateway's service account. When a recheck finds such a grant on a running Gateway, it reports over_privileged in a heartbeat before it stops, and the api records a gateway.over_privileged audit event.

    Connector advertised but nothing is bound¶

    The Gateway reports its connectors and targets in the catalog, but an advertised connector does nothing until an admin approves it and binds a target. In the detail view, check the connector's status:

    • advertised: approve it with POST /api/v1/admin/gateways/<id>/connectors/<connector-uuid>/approve.
    • approved but no entry under bindings: create a binding with POST /api/v1/admin/gateway-bindings.
    • missing: the Gateway no longer advertises this connector. Check the connector name in the chart values.

    A binding request that fails answers with a closed code. target_not_advertised means the argocd_target_id is not an application id in the connectors file, and target_stale means the Gateway advertised it once but no longer does.

    Gateway gets 401 from the control plane¶

    The log shows control plane refused this gateway; claiming stopped, staying up and not ready until restarted. The pod stays up and not ready on purpose, so it does not restart-loop. The api records gateway.auth.rejected.

    The usual cause is a revoked Gateway (status: "revoked" in GET /api/v1/admin/gateways). There is no rotation in Release 1: create a new Gateway, mint a token, enroll, replace the identity Secret and restart the Deployment. A disabled Gateway gets the same 401: enable it again (Enable… on its detail panel, or PUT /api/v1/admin/gateways/<id>/enabled) and restart the Deployment. If the Gateway is still active, the Secret holds a credential that does not belong to it, for example from an earlier enrollment.

    Observation stays pending, or shows "No observation configured"¶

    Check the request's observations first:

    curl -fsS -b "$JAR" "$CP/api/v1/requests/<request-id>/observations" \
  | jq '{observation_source, rollup, tasks: [.tasks[] | {gateway_name, state, verdict, attempt_count, deadline_at}]}'

    rollup: "none" means no task exists. Check observation_source and the audit events with the correlation_id of the job that executed the change:

    • observation_source is none: the environment is not set to gateway, so no task was created. none is the default, and environments that used the retired control-plane poller were moved to it at the cutover. With none, the audit log has request.observation_skipped with reason source_none. The source is read when the request reaches executed, so switching it later does not add tasks to earlier requests. See Switch the environment.
    • request.observation_skipped with reason no_gateway_binding: no enabled binding covers the secret in that environment, or the binding's Gateway is revoked or disabled, or its connector is not approved.
    • No skip event and no task: the binding exists, but the Gateway no longer advertises its target (target_stale), so it was skipped.
    • scope_not_resolved, request_type_not_observed or provider_type_not_supported: only patch and cross-team requests on aws-sm or vault secrets in an environment are observed.

    rollup: "pending" with a task in queued that never moves:

    • Not yet claimable. The first claim is allowed 10 seconds after executed, and a result that left the stage not_observed reschedules the task 15, 30, 60 and then 120 seconds later. Argo CD that stays Progressing or OutOfSync keeps the task in that loop until the deadline.
    • The Gateway is not claiming. Check its status in Admin → Gateways. A stale Gateway has missed its heartbeats; check the pods and their route to the control plane. A Gateway pauses claiming while the control plane is unreachable, its catalog is not accepted or a connector self-check fails (see Runtime behaviour). A Gateway that has never had a heartbeat accepted gets 204 on every claim.
    • The connector or binding changed. A task is claimable only while its binding is enabled and its connector approved.

    A pending task never fails the request. At its deadline it ends timed_out.

    Observation timed out with gateway_unavailable¶

    The deadline passed and the Gateway had not been seen since the task was created, or was not active (stale, disabled or revoked). Check the Gateway's status and its pod logs. A task is never handed to another Gateway, so the request stays timed_out; the next change to the secret gets a new task. deadline_reached instead means the Gateway was up but the stage was not observed in time.

    timed_out is not a failure of the request or of the deployment. Without the worker sweepers (SB_WORKER_GATEWAY_SWEEPERS_ENABLED), an overdue task is closed only when someone opens the request.

    Result rejected with attempt_superseded or task_closed¶

    The Gateway log shows result dropped: attempt superseded, result dropped: lease expired or result dropped: task closed, and the api records observation.evidence.rejected with a reason:

    • attempt_superseded (stale_attempt, unknown_attempt): the attempt is not the task's current one. Its lease ran out and the task was claimed again, it was released, or the Gateway was disabled or revoked while it held the lease. The newer attempt carries on. Frequent cases mean the Gateway works past its 60-second lease; check Argo CD latency.
    • task_closed: the task is already closed. A later change to the same secret (superseded_by_later_write), a source change (source_changed), a deleted binding (binding_removed) or the deadline closed it first.

    Neither needs action on its own. The verdict comes from the result that was accepted, or from the reason the task closed.

    Claim answers 429 inflight_limit¶

    The Gateway already holds max_inflight_tasks live leases (default 20), or the replica asking already holds one, which is the limit per replica. The Gateway backs off for the Retry-After time. Raise max_inflight_tasks when you create the Gateway, or add replicas, if tasks wait too long. The claim rate limit (2400 a minute per Gateway) answers 429 too.

    Useful queries against the audit log¶

    Find every action for one request¶

    curl -fsS "http://localhost:18080/api/v1/audit-events?correlation_id=<uuid>" \
  -b "$JAR" | jq '.[] | {time:.occurred_at, actor, action, resource}'

    Find every login failure in the last hour¶

    SINCE=$(date -u -d '1 hour ago' +%Y-%m-%dT%H:%M:%SZ)
curl -fsS "http://localhost:18080/api/v1/audit-events?action=auth.login&since=$SINCE" \
  -b "$JAR" \
  | jq '.[] | select(.status=="denied")'

    Find every wrap retrieval (who saw which value when)¶

    curl -fsS "http://localhost:18080/api/v1/audit-events?action=wrap.retrieve" \
  -b "$JAR" \
  | jq '.[] | {time:.occurred_at, actor, resource, status}'

    This is the SOC2-friendly query, every plaintext reveal across the platform, append-only, with the actor and timestamp.

    Reading the metrics¶

    The api and worker both expose Prometheus metrics at /metrics. The interesting ones:

    Metric What
    worker_scheduler_runs_total{task,outcome} Per-sweeper success / failure / skipped_lock counter
    worker_scheduler_run_duration_seconds{task} Sweeper latency histogram
    worker_scheduler_lock_skipped_total{task} Leader-election losses (expected for N-1 of N replicas)

    For HTTP-side latency, log-derived metrics are the source today; a future PR adds explicit histograms.

    When in doubt¶

    • Check the audit log first (GET /audit-events)
    • Then the api logs (docker logs secrets-bridge-api-1)
    • Then the agent logs (docker logs secrets-bridge-agent-1)
    • Then Postgres (docker exec -it secrets-bridge-postgres-1 psql -U secrets_bridge)
    • File an issue at secrets-bridge/.github with the correlation_id and the audit chain
